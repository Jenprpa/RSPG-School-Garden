# P0.1 Authentication Migration Plan

This document outlines the strategy for migrating the RSPG School Garden user authentication from the legacy insecure custom Firestore-based storage to the standard Firebase Authentication service.

## 1. Current Architecture (Legacy)
* **Authentication Storage**: Custom credentials stored in the `users` Firestore collection.
* **Credentials Format**: Plaintext password (`password` field) stored directly in the Firestore document under the document ID (which is the user's lowercase email).
* **Session Management**: Client application reads and trusts the login state and user role from browser `localStorage` under the key `rspg_logged_in_user`.
* **Password Reset**: Open reset flow that updates the Firestore password directly based only on the email presence, without any verification.
* **Sponsorship / Role Assignment**: Roles are sent from the client-side sign-up form directly, allowing any role to be registered.

## 2. Target Architecture (Secure)
* **Authentication Authority**: Firebase Authentication (Email/Password provider).
* **Session Restoration**: Authenticated session verified securely by `onAuthStateChanged` token observer from Firebase Auth.
* **Role/Profile Management**: The user profile is retrieved from Firestore `users/{email}`. The client-side role (`userRole`) is loaded dynamically from this profile after Firebase Auth verifies the token.
* **LocalStorage Usage**: LocalStorage is used only for non-security UI preferences (e.g., theme, active tab). `rspg_logged_in_user` is removed as a source of authority.
* **Password Reset**: Handled securely by Firebase Authentication's native `sendPasswordResetEmail` workflow.
* **Registration**: New signups automatically receive a default `student` role, with no ability to specify a higher role from the client.

## 3. Migration Approach: Forced Password Reset (Approach C)
Due to security constraints (preventing unauthenticated users from reading the `users` collection to verify plaintext passwords), we adopt the **Forced Password Reset** migration strategy:
1. **Auth Accounts Provisioning**: An admin script is executed using the Firebase Admin SDK to fetch all user records from Firestore and create corresponding Firebase Auth accounts with random secure temporary passwords.
2. **User Password Reset Action**: On their first attempt to log in to the new system, existing users will be notified that they must use the "Forgot Password" (ลืมรหัสผ่าน) feature to set a secure password.
3. **Password Update**: Firebase Authentication sends a secure verification link to the user's email. Clicking the link allows them to define their new password.
4. **Transition and Compatibility**: Plaintext passwords remain in Firestore temporarily as legacy fields for audit reference but are never read, compared, or written to by the production client application.

## 4. Data Mapping
* **Authentication User**:
  - `uid`: Generated by Firebase Auth.
  - `email`: User's lowercase email.
* **User Profile Document (`users/{email}`)**:
  - Document ID remains the user's email for backward compatibility and to minimize schema changes in this sprint.
  - Add metadata fields:
    - `authMigrated: true`
    - `authMigratedAt: ISO_TIMESTAMP`

## 5. Rollback Plan
If the migration encounters critical issues on production:
1. Revert client code changes to the legacy release tag.
2. The legacy login system will resume checking plaintext passwords in Firestore.
3. Users who changed their passwords will still be able to log in using their old passwords stored in Firestore (since the old passwords are not deleted during this phase).

## 6. Known Limitations & Risks
* **Email Access**: Users must have access to their registered email addresses to receive the password reset link.
* **Manual Setup**: Admin must enable the Email/Password sign-in provider in the Firebase Console before deployment.
* **Database Rules and Authorization Status**:
  - During client testing, anonymous (unauthenticated) read and write requests to the Firestore database were rejected with a `permission-denied` status.
  - The repository currently lacks rules-as-code configurations (`firestore.rules` and `storage.rules`).
  - Deployed production database and storage rules on the live Firebase console have not been audited or verified yet.
  - The authorization status (access control constraints) remains unverified on the backend and must be validated and enforced in Sprint P0.2 (Firestore Rules) and P0.3 (Storage Rules) to lock down the database against malicious authenticated clients.

## 7. Deployment Order
1. **Console Action**: Enable Email/Password provider in the Firebase Authentication Console.
2. **Admin Import**: Run the Admin SDK migration script to provision Auth accounts for all existing users.
3. **App Deployment**: Build and deploy the client code changes to Firebase Hosting.
